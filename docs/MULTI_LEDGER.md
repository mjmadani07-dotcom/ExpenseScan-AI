# Multi-ledger Android development

Branch: android-multi-ledger. Baseline: 48a41106b2bf7e9e402d90e8d1b516fbfd938bfb. Do not merge or publish this branch until explicit acceptance. Stable signing remains separate.

## Product decisions
- A workspace is an independent financial ledger, not an account/login. One unlocked device owner can access all workspaces. Separate categories, budgets, rates, drafts and recovery checkpoints; shared physical encrypted attachment storage and device authentication. No cloud sync or multi-user access.
- Creation, rename, color, archive/unarchive; no hard delete in first release. Archive requires resolving pending drafts. At least one active workspace; 100-workspace initial safety cap.
- Active entry scope is exactly one workspace; reports explicitly select one or more workspaces including archived if intentionally selected. Never include personal in corporate aggregation by default. Display unit shared; canonical totals computed in toman using each source document's historical FX and source ledger fallback. Category IDs are local, not global; disambiguate by ledger ID. Preserve record identity as (ledgerId, recordId).
- Original database migrates losslessly to one neutral default "دفتر اولیه"; user renames it. Never guess existing records' location. Move documents only by explicit transactional action, with category mapping and original identity/attachment checks.

## Phase 2 implementation (not enabled for users)
Native `MultiLedgerTables` schema 4 uses encrypted profile and per-entity row envelopes bound to ledger ID, table, ID and parent. Scoped composite foreign keys prevent children crossing workspace boundaries. v3→v4 copies exact decrypted rows, verifies each row before dropping v3 tables, and increments the existing global revision within the same transaction. Native session-gated bridge and opt-in AndroidMultiLedgerStore are implemented; v0/v1/v2 first normalize via the current v3 path. Global attachment reference scan includes all workspaces. Existing AuthGate remains single-ledger: no automatic migration or installable multi-ledger release. Branch emulator runs dedicated actual SQLite/Keystore migration, rollback, FK, stale revision, encrypted transplant and reopen regression. Current transport reads entire catalog and caps commit payload at 64 MiB; optimize scoped reads/patches before large datasets. Full backup/restore, UI and end-to-end migration acceptance remain gating items. Phase 1 UUID default type inference corrected.

## Phase 3 implementation (internal-only)

App displays the active ledger in the header and capture; switching is via overview → catalog. Session refuses pending queued writes, compares the visible draft to its saved form, disposes the prior repo before opening another. Child busy signals guard navigation for capture, PDF/Excel, record mutation and settings actions. No destructive workspace removal. Single-ledger portable backup and GC UI are withheld in multi-ledger mode. User-selected unit remains shared; no auto-selection of corporate versus personal scopes. Developer-only `VITE_MULTI_LEDGER_INTERNAL=true` enables the shell on native Android for a fresh test DB or previously migrated internal schema 4, refuses v1-v3; normal build uses the existing single-ledger AuthGate. Do not distribute internal builds for real records. UI static-render and session lifecycle tests added; full physical UI, report naming, unsaved settings, full backup, transfers and end-to-end upgrade acceptance remain outstanding. ## Phase 5A: portable archive codec (internal foundation)
ESBACK3 is a distinct authenticated streaming format using the v2 framing engine (PBKDF2-SHA256 600,000, AES-256-GCM, ordered frames, final authenticated terminator). The all-ledger manifest preserves IDs, archive state, financial data, drafts and recovery checkpoints; excludes AI configurations and replay acknowledgement tokens. Attachment hashes are deduplicated globally and verified before the manifest can be returned. Existing ESBACK2 API/magic remains separate. The codec stages immutable attachments only; atomic native replacement, v1/v2 import routing, UI confirmation, native file publication and actual restore/device tests remain gated. No production activation.

## Phase 5B: atomic restore foundation (internal only)
Dedicated native restore path uses the exact revision, validates profiles and rows, verifies original attachment digests, and replaces the entire catalog inside one SQLite transaction. Normal commit remains non-destructive. Readback verifies every restored profile/row before advancing revision. The session requires a matching preview, full authenticated archive and a separately published safety backup before restore; stale revision refuses replacement. Native ESBACK3 staging recognizes the new extension and checks magic. UI confirmation/publication, legacy v1/v2 import as a separate ledger and actual end-to-end restore remain gated. Staged orphan attachments may remain on failed restoration; existing referenced originals are never deleted by restore.

## Mandatory owner feedback / release gates
- [ ] Camera/file selection lasting more than five minutes: resume the exact ledger and capture workflow after reauthentication; do not silently restart or resubmit. Persist only minimal non-sensitive navigation identifiers and encrypted draft/attachment checkpoints. Never extend authentication indefinitely or store financial data in plaintext localStorage.
- [ ] Android process death while camera/file chooser is open: preserve recoverable input and workflow identity, reconcile pending picker result where Android permits, show an explicit retry/recovery state if the result cannot be recovered. Exercise cancellation, long background, forced process death, screen lock and restart; no cross-ledger write, duplicate expense or lost committed draft. Raw unreturned camera data may be unrecoverable, communicate that limitation.
- [ ] Physical phone acceptance: verify four feedback fixes (long capture/file selection, reduced repetitive authentication, grouped amount fields with Persian/Arabic digits and decimal precision, JSON export with correct contents and location), plus v3 full restore and signed upgrade. Record model, Android version, exact commit, APK and signer checksum; synthetic data only until acceptance. Emulator success is not physical-device acceptance.

## Phase 5C: all-ledger backup UI (internal only)
Catalog includes an independent backup screen. Export uses verified native publication of ESBACK3. Restore displays incoming ledger identities/counts and archive/draft status, requires explicit confirmation plus repeated password, fully authenticates the archive and publishes a separate safety backup encrypted with that password before attempting revision-bound native replacement. On older Android SAF backup copy now verifies SHA-256 readback. The emulator scenario exports an archive, adds a temporary ledger, restores through the real UI, checks safety backup and both restored scopes. File selection is synthetic DataTransfer, not a physical camera/picker. Legacy import, lifecycle recovery, large archive and physical-device/signed-upgrade gates remain outstanding.

## Phase 5D: legacy import
Encrypted v1 and ESBACK2 archives are imported into a new named ledger only, using the normal append-only CAS. Full ESBACK3 replacement remains separate. Wrong password, invalid/truncated archive, duplicate names and stale revisions must not replace existing ledgers. Existing originals are staged by hash. CI and physical device tests remain required.
